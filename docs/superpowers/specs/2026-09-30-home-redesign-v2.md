## 1. 背景

2026-09-29 的「维修主导」改版是在平台只有**维修 + 回收**两个业务时做的，首页结构为
「维修主卡 → 三保障 → 热门维修 chips → 回收次卡 → 热门机型」。

之后新增了**「购买」（严选二手机）**业务并占据第 2 个 tab，但首页完全没有它的位置；
同时首页缺少**搜索入口**，也没有承载「官方质检」这一最核心的信任卖点。

## 2. 信息架构（自上而下）

| 顺序 | 模块 | 作用 | 与旧版关系 |
|---|---|---|---|
| 1 | 定位 + 全局搜索 | 降低寻找成本，覆盖机型/故障/二手机 | 新增 |
| 2 | 维修主卡（浮起大卡） | 平台定位锚点，最强 CTA | 视觉强化 |
| 3 | 回收 / 购买 双卡 | 两条业务并列，各带价格钩子与 CTA | 新增购买 |
| 4 | 哪里坏了（5 宫格） | 维修最高频入口 | 横滑 chips → 宫格 |
| 5 | 严选二手机横滑 | 购买业务转化位，卡片带成色 + 质检标 | 新增 |
| 6 | 热门机型回收横滑 | 保留品牌预选估价链路 | 原样保留 |
| 7 | 服务保障四宫格 | 三项保障 + 官方质检统一背书 | 顶部保障行 → 底部四宫格 |

## 3. 关键设计决策

1. **维修仍是唯一主卡**：维修占满整行并浮在头部之上，回收与购买各占半宽 —— 维持「维修主导」定位，
   同时给新业务合理曝光，不做三业务平均用力。
2. **头部渐变延伸到状态栏**：品牌色大色块建立记忆点；搜索框压在渐变上形成层次；
   维修主卡以负边距上浮制造卡片感。
3. **每个业务卡都带钩子数字**：回收「最高 ¥3200」、购买「¥1299 起」，用价格锚点替代抽象描述。
4. **故障入口由横滑改宫格**：横滑会把「其他故障」藏在屏外，宫格一屏看全且点击目标更大。
5. **质检前置**：官方质检同时出现在搜索副标题、购买卡副文案、商品卡绿色标、底部保障宫格 ——
   二手交易最需要反复强化的信任点。
6. **保障区下沉合并**：原顶部三保障占一行且挤占首屏，现与「官方质检」并列下沉到页面底部。

## 4. 跳转与数据来源

| 模块 | 点击去向 | 数据来源 |
|---|---|---|
| 维修主卡 / 快捷故障 | 维修 tab | 静态（故障项前端常量） |
| 旧机回收卡 | 回收 tab（估价） | 静态钩子价 |
| 严选二手机卡 / 商品卡 | 购买 tab → 商品详情 | GET /api/wx/goods（已就绪，支持品牌/成色筛选） |
| 热门机型卡 | 回收 tab + 品牌预选（storage recycle.prefillBrandId） | fetchHome() 的 hotModels（已就绪） |
| 搜索框 | v1 跳购买 tab；v2 做聚合搜索页 | — |

小程序落地页：pages/home/home.{js,json,wxml,wxss}（预计还需 home.js 增加严选商品拉取）。

## 5. 待用户确认

1. **购买 tab 的位置**：当前为「首页 / 购买 / 维修 / 回收 / 我的」，购买排在维修之前。
   若维修仍是主推，是否改为「首页 / 维修 / 购买 / 回收 / 我的」？
2. **搜索框 v1 行为**：先跳购买 tab（成本低），还是直接做机型/故障/商品三合一的聚合搜索页？
3. **钩子数字**：卡上的「最高 ¥3200」「¥1299 起」是用接口实时取（回收最高估价 / 购买最低在售价），
   还是先由运营配置？

## 6. 落地后的验证方式

1. 小程序开发者工具「清缓存后编译」，走查：搜索框、维修主卡、双业务卡、故障宫格、严选/热门横滑、保障宫格、下拉刷新。
2. 各卡跳转与参数传递：热门机型 → 品牌预选 → 估价页已选中品牌；严选商品卡 → 商品详情。
3. 无库存/无热门机型时的降级表现（对应区块隐藏或空态，不出现空白卡）。
