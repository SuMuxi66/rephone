# 支付订单自动关闭设计（V1.2.1 仅设计，不实现）

日期：2026-10-08 ｜ 状态：待排期 ｜ 关联：payment_order / PaymentService / RepairPaymentFlowTest

## 背景

用户在 38 待支付态发起支付后若弃付，`payment_order` 会留下 PENDING 单。当前 `start()`
对同订单复用 PENDING 单（payNo 不变），功能上自洽，但存在两个问题：
1. PENDING 单无限期残留，对账口径含大量"僵尸单"；
2. `out_trade_no` 长期占用微信侧未关闭订单。

## 方案（建议：定时关闭 + 复用收紧）

### 1. 超时关闭

- 定时任务（Spring `@Scheduled`，每小时）：扫描 `status=0 AND create_time < now()-2h` 的
  payment_order，批量 CAS 置 `status=2 CLOSED`。
- 真实模式下关单前调微信 V2 `closeorder`（out_trade_no=payNo），避免微信侧稍后支付成功
  与本地 CLOSED 冲突；mock 模式跳过出网。
- 关单后收到迟到的支付成功回调：`markPaySuccess` 对 CLOSED 单返回 false → 回调 FAIL，
  微信重试后仍 FAIL（本地已关单且未入账，资金侧以微信退款流程处理——联调时确认该边界，
  2 小时窗口内微信侧支付概率极低）。

### 2. 复用收紧

`start()` 当前复用同订单任意 PENDING 单；改为只复用 `create_time > now()-2h` 的单，
过期 PENDING 视同关闭、新建支付单（新 payNo）。微信 V2 不同 out_trade_no 互不影响。

### 3. 状态机与幂等

- CLOSED 为终态：`markPaySuccess`/`closePending` 对 CLOSED 单不做任何变更。
- 订单侧不受影响：38→30 仅由「已接受报价 + 支付成功回调」驱动，关单后用户重新支付
  会生成新支付单，回调照常推进。

### 4. 配置

`rephone.pay.pending-ttl=2h`、`rephone.pay.close-cron=0 0 * * * *`（环境变量可覆盖）。

### 5. 测试要点

TTL 边缘（1h59m/2h01m）、关单后迟到回调 FAIL、关单后重新支付生成新 payNo、
closePending 与定时关闭并发（CAS 幂等）。

### 影响面

仅 PaymentService + 新增定时任务；无表结构变更（status=2 已预留）；无 API 变化。
