# 维修报价流程实施计划（需求 V1.1 第二优先级）

日期：2026-10-08 ｜ 分支：feature/recycle-mvp ｜ 状态：进行中

## 目标

维修流程在既有「价目预约直修」之外，增加「检测 → 报价 → 用户确认 → 支付 → 维修」报价模式，
复用现有订单体系/租户隔离/RBAC/支付体系，不动既有状态语义与接口。

## 关键决策（兼容性核心）

- **状态编号增量扩展，不改动既有值**：在 RepairOrder 上新增
  15 待检测(WAIT_INSPECTION)、35 待报价(WAIT_QUOTE)、36 待确认报价(WAIT_CONFIRM_PRICE)、38 待支付(WAIT_PAYMENT)；
  维修中复用 30、完成复用 50（支付成功 → 30，与需求「REPAIRING→COMPLETED」对应到现有 30→…→50 链）。
  既有 10/20/25/30/40/45/50/80 的语义与流转全部保留 —— 直修模式原路径可用，报价模式是叠加路径。
- **报价模式判别**：详情接口新增 `quote` 字段（最近一次报价，null=未走报价）；
  前端时间线按 `quote != null || status∈{15,35,36,38}` 切到报价流程视图。
- **推进边**：上门 10→{20,15}、20→{30,15}；寄修 10→{20,15}、25→{30,15}；两边 15→35；
  报价提交 35→36（专用接口）、用户接受 36→38、用户拒绝 36→20（退回已预约/待寄出，可重新检测报价）、
  支付成功 38→30。40/45/50 及取消规则不变。
- **金额口径**：repair_quote.quote_amount 用 DECIMAL(10,2) 元（与 repair_item_price 同口径，需求明确要求 decimal）；
  API 传输一律分（AGENT.md 硬规则），服务层互转。
- **支付**：抽公共 `PaymentService`（SALE/REPAIR 业务类型参数），出售 `MOCKPAY-` 流水号格式不变；
  repair_order 增加 `pay_no` 列（存量库走 patch-repair-quote.sql）。
- **接口落位**：按仓库惯例挂 `/order/{orderNo}/` 段（需求原文少了 order 段，见交付说明）：
  POST /api/admin/repair/order/{orderNo}/quote、GET /api/wx/repair/order/{orderNo}/quote、
  PUT /api/wx/repair/order/{orderNo}/confirm-price|reject-price|pay。

## 非目标

- 不接真实微信支付（PaymentService 预留扩展点，仍 mock）。
- 不改直修模式的任何既有流转/页面交互；不新增订阅消息推送（维修域现状无推送）。
- 不动回收/出售流程与评价系统。

## 任务 / 提交拆分

1. `docs(plans)`：本计划。
2. `feat(server)`：schema+patch、实体/DTO/Mapper、PaymentService 抽取、维修报价/确认/拒绝/支付接口、
   RepairQuoteFlowTest（独立 H2 库，七类场景）。
3. `feat(admin)`：维修单详情「开始检测/检测完成/提交报价」操作与新状态字典。
4. `feat(miniprogram)`：repair-status 新状态与报价时间线、quote-confirm 页、详情页报价/支付接线。

## 验收标准

- RepairQuoteFlowTest 覆盖：正常报价链、拒绝后退回可重报、未登录 401、跨租户隔离 404、
  重复报价拒绝、非法流转拒绝、支付成功 38→30 且落 pay_no。
- 既有 P7RepairFlowTest / RepairMailInFlowTest 不回归（直修/寄修原路径不变）。
- 管理端与小程序可完成完整报价链（静态校验通过）。

## 风险

- 门禁会话为拦截模式：提交沿用「涉事文件+miniprogram_npm 移出 → 临时索引提交 → 移回」姿势。
- RepairOrderDetail 为 record，追加字段需同步 toDetail 单处构造（无其他调用方）。
